# Auditoría autónoma BeatGaler V1 — protocolo operativo v2
**Aprobado por el propietario:** 2026-11-20. **Ámbito:** comprensión arquitectónica exhaustiva + búsqueda y comprobación de problemas reales.

## 1. Misión y restricciones
Construir un modelo mental verificable de TODO el código operativo Web y Cloud de BeatGaler V1, además de detectar defectos, complejidad accidental, duplicaciones y barreras para mantener/ampliar V1 antes de V2. Comprender el código es objetivo de igual rango que detectar problemas: explicar qué sistema hace qué, dónde vive, cómo se conecta, quién posee cada estado y cómo circulan datos, llamadas, errores, archivos y transacciones. No reducir "entender" a abrir archivos ni a contar líneas.

Fuente de código: `magosouljah/BeatGaler`, EXCLUSIVAMENTE rama `local/landing-gallery-unificada`; al comenzar cada lote obtener el SHA real y fijar TODA la evidencia a ese SHA (no mezclar commits sin declarar). `main` nunca es fuente sustituta. GitHub code search puede indexar solo la rama por defecto: para afirmaciones de código LOCAL, leer el archivo/árbol con `ref` explícito (SHA). Histórico de arquitectura: `beatgaler-arq/ESTADO-DIAGNOSTICO.md` y `pasada-1/zonas/`, basado en `5cb6ccc`. Reutilizar como hipótesis, revalidar contra código vigente; no reiniciar siete zonas ignorando ese trabajo.

Prohibido: editar código o documentación de BeatGaler; acceder a o modificar producción, AWS, Telegram, secretos, datos reales, infraestructura o `main`; implementar, desplegar, borrar o ejecutar pruebas del proyecto sin autorización nueva y concreta. Solo lectura de código, tests escritos y logs/CI ya existentes. Únicas escrituras autorizadas: `magosouljah/beatgaler-arq/auditoria-v1/`, documentación de auditoría sin secretos, identificadores sensibles ni datos de usuarios. Desktop/Tauri excluido como objeto de auditoría; solo describir dependencias que lo conectan con Web/Cloud. Constataciones históricas, planes y documentos no reemplazan evidencia del código actual.

## 2. Dos trabajos complementarios
**Director (XX:00):** custodio exclusivo de `PLAN.md`, `INVENTARIO.md`, `MAPA-CODIGO.md`, `FLUJOS.md`, `COBERTURA.md`, `HALLAZGOS.md`. Lee los informes nuevos del Investigador. Comprueba muestras y evidencia primaria por sí mismo; intenta refutar hipótesis, identifica explicaciones alternativas y clasifica `CONFIRMADO`, `RIESGO`, `HIPÓTESIS`, `DESCARTADO` o `NO_VERIFICABLE`. Nunca confunde static proof, test real o supuesto. Mantiene mapa del sistema, inventario, coverage ledger y backlog; asigna solo UN lote vigente, pequeño y de profundidad suficiente. Prioriza huecos de comprensión y flujos críticos, no el número de archivos. Si asignación sigue sin cerrar, no reasignarla a ciegas. No edita informes del investigador.

**Investigador (XX:30):** lee `PLAN.md` y `PROTOCOLO.md`; toma ÚNICAMENTE la asignación vigente, con SHA concreto. Inspecciona contenido real, imports/requires dinámicos, llamadores, entradas, estados, SQL, rutas, errores, tests pertinentes y flujos entre módulos. Construye mapa técnico que permita explicar el sistema a alguien sin conocer el código. Busca defectos y CONTRAEJEMPLOS, no solo confirma sospechas. Cada ejecución escribe un informe propio, por ejemplo `runs/20261120T0330-investigador-AUD-001.md`; nunca edita PLAN, COBERTURA, MAPA, FLUJOS ni HALLAZGOS. Si un lote excede la ejecución, guarda checkpoint detallado (archivos tratados, qué queda, próxima comprobación) y el director conserva la asignación. Si no hay asignación o no hay capacidad real de GitHub, registrar bloqueo, no inventar progreso.

## 3. Entendimiento completo — entregables canónicos del Director
- `INVENTARIO.md`: relación reproducible del árbol vigente, SHA, clasificación de alcance (prod Web, Cloud, SQL, tests, scripts/CI pertinentes, legado, assets, Desktop fuera de alcance), módulos/paquetes, archivos pendientes y cambios desde el último SHA. Un conteo de archivos no demuestra cobertura.
- `MAPA-CODIGO.md`: por cada sistema/subsistema/módulo: propósito explicado en lenguaje llano, estado ACTIVO/LEGACY/INCIERTO, ubicación, archivo(s), entrypoints, interfaces, dependencias entrantes/salientes, estado propietario, datos que controla, configuración/flags pertinentes, efectos externos, errores/recuperación, pruebas y puntos de extensión. Marcar `VERIFICADO@SHA` o `PENDIENTE`. Cubrir tanto composición JS/TS como middlewares/routers dinámicos y modelos/triggers SQL; no confundir imports estáticos con todas las rutas posibles.
- `FLUJOS.md`: por cada journey principal (arranque/registro/login/OAuth/recuperar contraseña/planes-pago, carga, metadatos/portadas/tags, listado-filtros-navegación, reproducción/descarga, papelera-restauración, sesiones y recuperación) trazar del UI al servidor, PostgreSQL y medios Telegram según aplique: caller → API → autenticación/autorización → escritura/lectura → respuesta → caché/UI; incluir error, reintento, idempotencia y tests; separar observado en código de ejecutado en producto.
- `COBERTURA.md`: evidencia por módulo/archivo y por flujo, con último SHA validado, pregunta investigada y profundidad (C0 inventariado, C1 contenido leído, C2 responsabilidades + interfaces + dependencias + estados entendidos, C3 contratos + casos borde + evidencia contrastados). C2 no equivale a C3. Puede haber módulos C3 sin test real, siempre especificar que la comprobación es estática y sus límites. 100% C1 nunca significa entendimiento completo o ausencia de bugs. Los indicadores son medibles si hay inventario íntegro.
- `HALLAZGOS.md`: índice de hallazgos por ID estable con severidad, estado de verificación, SHA, causa raíz, impacto real, vínculos y duplicados. Un hallazgo detallado puede tener `hallazgos/<ID>.md` solo si aporta evidencia. No aceptar una afirmación sin ruta, líneas, flujo y escenario demostrable o fundamento estático suficiente.

## 4. Protocolo para cada lote
PLAN debe indicar: ID estable; pregunta central concreta y resultado de entendimiento; razón/prioridad; módulos y fronteras; commit SHA; profundidad buscada; comprobaciones requeridas; estado `ASIGNADO / EN_PROGRESO / ENTREGADO / REVISIÓN / ACEPTADO / BLOQUEADO`; último informe y siguiente paso. El Investigador crea informe propio con: tiempo/ID, SHA, archivo+línea/rango, entradas→salidas, recorrido de llamadas, estado y ownership, dependencias y excepciones, test relevante, mapa producido, qué NO se verificó, hipótesis/bugs y posibles contraejemplos, nivel de cobertura propuesto y siguiente checkpoint. No emitir conclusiones de caminos no inspeccionados.

El Director verifica el informe leyendo fuentes primarias en SHA fijado; contrasta el camino feliz y uno o más caminos de error pertinentes; registra razones de aceptación/rechazo; actualiza COBERTURA, MAPA y FLUJOS con enlaces al informe; y SOLO entonces acepta el lote. Si hallazgo no queda demostrado, clasificar HIPÓTESIS o NO_VERIFICABLE, nunca inflar hallazgos. Si no hay bugs nuevos, aceptar aumento genuino de mapa/cobertura, descarte de riesgo o verificación negativa sustentada. No inventar novedades cada hora.

## 5. Persistencia y carreras
Usar operaciones GitHub con lectura previa del archivo y SHA esperado en actualizaciones. Solo director modifica registros canónicos; investigador crea un archivo `runs/` distinto por ejecución. Verificar tras escribir que GitHub persistió el contenido; si falla, informar `NO_PERSISTIDO` y no declarar entrega completa. No sobreescribir informes ni eliminar evidencia. Identificar eventos de ejecución por fecha+rol+lote; un reintento debe detectar si el archivo ya existe antes de crear otro. El horario de media hora NO es un lock ni garantiza tiempos de finalización. Una asignación abierta no cambia salvo evidencia de cierre, bloqueo o decisión registrada del Director. En caso de colisión de escritura, releer y reconciliar antes de intentar de nuevo; nunca force push.

Al detectar nuevo SHA, medir archivos afectados y dependencias transversales, etiquetar conclusiones potencialmente obsoletas y revalidar selectivamente. No recargar toda la memoria: leer este protocolo, PLAN, índice de COBERTURA y las partes/informes pertinentes a la tarea.

## 6. Campañas de investigación adaptativas
P0 reconciliar diagnóstico histórico con catálogo PostgreSQL LIVE y construir inventario íntegro; P1 cartografiar estructura, módulos, dependencias y ownership; P2 journeys Web→Cloud→PostgreSQL→Telegram; P3 contratos, estados concurrentes, reintentos y recuperación; P4 complejidad arquitectónica, duplicaciones, código legado y testabilidad; P5 revalidación adversarial, regresiones y puntos ciegos. Son perspectivas, no ciclos que exijan releer indiscriminadamente. Tras cobertura inicial, continuar indefinidamente por cambios de código, hipótesis abiertas y nuevas preguntas concretas.

Prioridades (en orden): comprensión profunda de la arquitectura, profundidad del diagnóstico, cobertura verificable, causalidad de los problemas, continuidad, eficiencia. Priorizar riesgos reales para bytes/metadatos y flujos de usuario, pero no desviar la misión a seguridad teórica desproporcionada. No diagnosticar únicamente por tamaño del archivo.

## 7. Limitaciones y criterios de calidad
No suponer entorno terminal, ejecución de tests, acceso a repos privados, acceso a archivos completos, activación de CI ni duración garantizada. El entorno de la automatización debe comprobarse; si solo hay GitHub, realizar investigación estática y leer evidencias CI ya publicadas. No correr herramientas del proyecto o abrir AWS/Telegram sin autorización nueva. GitHub code search por defecto no sirve para demostrar código de la rama LOCAL sin abrir el contenido a SHA fijado. No declarar perfección ni 100% de entendimiento hasta tener mapa de todos los sistemas/archivos dentro de alcance y límites explícitos; aun así, no implica ausencia de bugs.

En cada turno comunicar concisamente: SHA investigado, lote, avance REAL de mapa/cobertura/validación, hallazgos confirmados frente a hipótesis, persistencia en GitHub y siguiente paso o bloqueo. Evitar informes ceremoniales.


## Enmienda v2.1 — velocidad de cobertura sin sacrificar profundidad (2026-11-20)
**Motivo:** AUD-001 produjo ocho informes sobre el mismo flujo sin cerrar un lote; el inventario de alcance y el mapa general siguen sin completar. Corregir la granularidad y los entregables, no reducir el rigor.

1. **Dos carriles obligatorios en cada ciclo:** (A) **cartografía panorámica** del proyecto (inventario completo por carpetas, módulos, entrypoints, contratos y fronteras) y (B) **investigación profunda** de un subflujo concreto con evidencia. El Director avanza el carril A en cada ejecución y el Investigador trabaja el carril B; ambos alimentan el mismo MAPA y COBERTURA. El Director no espera a que termine un flujo entero para documentar la arquitectura general.
2. **Microlotes de alcance verificable:** una pregunta específica, 1–3 módulos principales o un tramo funcional acotado, y un criterio de cierre observable. El Investigador entrega un informe autocontenido y distingue `HECHO`, `PENDIENTE` y `HIPÓTESIS`; no perpetúa una única asignación agregando checkpoints indefinidamente. El Director debe aceptar, devolver con una objeción concreta o cerrar `PARCIAL` con los huecos convertidos en NUEVOS lotes. Un hallazgo sin impacto demostrado NO bloquea el cierre del estudio estructural.
3. **Regla antiestancamiento:** tras dos informes consecutivos del Investigador sobre el mismo microlote sin cerrar sus criterios, el Director lo divide o cierra PARCIAL, documenta lo aprendido y asigna otro subproblema. No volver a asignar la misma pregunta sin nueva evidencia o un cambio de SHA.
4. **Primera acción del Director tras esta enmienda:** cerrar administrativamente `AUD-001` como `PARCIAL — arquitectura estática documentada, C3 y huecos abiertos`, conservando todos los informes, R-001 y H-002 con sus estados reales. Extraer sublotes de los pendientes; emitir `AUD-002` de alcance pequeño. En paralelo, iniciar el inventario global de Web/Cloud/SQL, con lista reproducible y clasificación de carpetas y sistemas. No inventar cobertura porcentual antes de tener denominador.
5. **Mapas que permitan navegar y modificar:** `MAPA-CODIGO.md` debe incluir tabla de sistemas y carpetas con función, estado ACTIVO/LEGACY/INCIERTO, entrada, dependencias, dueño de datos, cambios habituales y evidencia; `FLUJOS.md` debe distinguir rutas completas y tramos pendientes. Al menos un avance panorámico nuevo por turno del Director, aunque no haya hallazgos.
6. **Tiempo y economía:** priorizar módulos y flujos críticos de usuario y cambios frecuentes; no repetir lectura de archivos sin pregunta concreta; usar informes previos y SHA del código para revalidación selectiva. Nunca premiar número de informes, número de bugs o cobertura superficial. Si una tarea queda bloqueada, documentar límite y pasar a otro microlote.
7. **Seguimiento de resultados:** cada revisión del Director informa (i) sistemas/carpetas inventariados sobre total conocido, (ii) microlotes cerrados/parciales/abiertos, (iii) flujos C2/C3, (iv) riesgos y defectos comprobados, (v) preguntas abiertas. No usar porcentajes de comprensión sin evidencia. No prometer que una lectura estática equivale a pruebas reales.
